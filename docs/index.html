K8s LLM Incident Analyser

A FastAPI service that collects Kubernetes pod diagnostic evidence, preprocesses and redacts it, sends it to an LLM under a strict JSON schema, and returns a structured IncidentReport — turning a manual, time-consuming pod-failure investigation into an automated, schema-validated pipeline.

01Executive Summary #

What the system does, the problem it solves, and the capabilities that make it a defensible research artefact.

The Problem #

When a Kubernetes pod enters CrashLoopBackOff, ImagePullBackOff, or starts restarting repeatedly, an on-call engineer must manually run a sequence of kubectl commands — logs, describe, get events — read through hundreds of log lines, mentally filter noise from signal, correlate events across resources, and form a hypothesis about the root cause. This is slow, repetitive, and inconsistent across engineers of different experience levels. The cognitive load is highest exactly when time pressure is greatest: during an active incident.

The Solution #

The K8s LLM Incident Analyser automates that workflow. Given a namespace and pod name, it runs a five-stage pipeline — collect → preprocess → redact → analyse → validate — and returns a single structured IncidentReport containing the likely root cause, the supporting evidence that led to that conclusion, a severity and confidence score, a suggested fix, recommended commands, and human verification steps. The LLM is constrained by a Pydantic schema, so the output is always machine-parseable, never free-form prose.

  • Pluggable LLM layer. Swap between Mock, OpenAI, Anthropic, and DeepSeek via a single LLM_PROVIDER environment variable — no code changes.
  • Schema-locked output. Every provider returns the same IncidentReport Pydantic model; the validator rejects malformed LLM output before it reaches the caller.
  • Privacy by design. Seven regex patterns mask API keys, passwords, database URLs, bearer tokens, and emails before any text leaves the cluster.

06Application Bootstrap #

How the FastAPI application is constructed, wired together, and exposed — 30 lines that anchor the whole service.

App Construction (app/main.py) #

The entire application bootstrap is 30 lines. A single FastAPI instance is created with title, description, and version; CORS is opened for all origins; three routers are mounted under their prefixes; and a /health endpoint reports the configured provider.

app/main.pyimport os

from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

from app.api import analyse, reports, scenarios

app = FastAPI(
    title="K8s LLM Incident Analyser",
    description="LLM-assisted Kubernetes incident analysis pipeline",
    version="0.1.0",
)

app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
    allow_methods=["*"],
    allow_headers=["*"],
)

app.include_router(analyse.router, prefix="/analyse", tags=["Analysis"])
app.include_router(reports.router, prefix="/reports", tags=["Reports"])

if os.environ.get("ENABLE_SCENARIOS", "false").lower() == "true":
    app.include_router(scenarios.router, prefix="/scenarios", tags=["Scenarios"])


@app.get("/health", tags=["Health"])
def health():
    return {"status": "ok", "provider": os.environ.get("LLM_PROVIDER")}

Key Decisions #

  • Wildcard CORS. allow_origins=["*"] keeps the prototype frictionless. In production this should be narrowed to the known UI origin.
  • Conditional scenarios router. The /scenarios endpoint is off by default — it lists filesystem scenario directories, which is useful during evaluation but unnecessary in a pure analysis deployment.
  • Stateless singletons. KubernetesCollector(), LogPreprocessor(), and LogRedactor() are instantiated once at module import in analyse.py (lines 16–18) and reused across requests. They hold no per-request state.
  • Provider per request. get_provider() is called inside the request handler, not at import, so changing LLM_PROVIDER takes effect without a restart in some deployment patterns.

The Analysis Endpoint (app/api/analyse.py) #

This is the heart of the system. A single POST triggers the entire pipeline, persists the result, and returns the structured report. A request ID (first 8 chars of a UUID) is logged at start and completion for traceability.

    request_id = str(uuid.uuid4())[:8]
    log.info("analysis_started", id=request_id, ns=namespace, pod=pod_name)

    try:
        raw = collector.collect(namespace, pod_name)
        filtered = preprocessor.process(raw)
        safe = redactor.redact(filtered)
        provider = get_provider()

        try:

        except Exception as persist_err:

        return report

        raise HTTPException(status_code=500, detail=f"Analysis failed: {e}")
Resilience pattern

Persistence failure is logged as a warning, not propagated. The report is still returned to the caller — saving to disk is a side-effect, not part of the contract. A pipeline failure, by contrast, becomes an HTTP 500 with the error detail.

Defensive design

Every _run() call returns an empty string on non-zero exit or TimeoutExpired — the collector never raises. This means a missing --previous log (common for a pod that has never restarted) simply yields previous_logs="" rather than crashing the pipeline.

8.2 Preprocessor app/core/preprocessor.py · 86 lines #

The preprocessor turns raw text into signal. It classifies each log line as noise (health checks, metrics, blank lines) or signal (errors, OOM, CrashLoopBackOff, refusals), keeps a configurable context window around each signal line, deduplicates, and caps the output. The goal: send the LLM the few lines that matter, not 500 lines of probe traffic.

Context-window filtering algorithm #

The _filter_with_context() method (lines 50–69) implements a three-step reduction:

  1. Mark. For each line, if it matches a signal pattern AND not a noise pattern, mark indices [i - context_window, i + context_window + 1] for keeping. Default window is 3 lines on each side.
  2. Deduplicate. Walk the kept indices in order; skip lines whose stripped content has already been seen.
  3. Cap. Return the first max_log_lines (default 100) joined with newlines.

Why this matters

A pod in CrashLoopBackOff generates dozens of GET /health and GET /ready probe log lines per minute. Without filtering, those drown the single RuntimeError that explains the crash. The context window preserves the lines around the error — often a stack trace — without keeping the noise.

The validator is the safety net for any provider that returns free-form JSON (notably DeepSeek, which uses json_object mode rather than structured outputs). app/core/validator.pyclass ReportValidator:
    """Validate LLM output against the IncidentReport schema."""

    def validate_dict(self, data: dict) -> IncidentReport:
        return IncidentReport.model_validate(data)

    def validate_string(self, raw: str) -> IncidentReport:
        try:
            data = json.loads(raw)
        except json.JSONDecodeError as exc:
            raise ValueError(f"Invalid JSON: {exc}") from exc
        if not isinstance(data, dict):
            raise ValueError("JSON must be an object, not a scalar or array")
        return self.validate_dict(data)

    def validate(self, data: dict | str) -> IncidentReport:
        if isinstance(data, str):
            return self.validate_string(data)
        return self.validate_dict(data)

    def get_schema(self) -> dict:
        return IncidentReport.model_json_schema()

    def is_valid(self, data: dict | str) -> bool:
        try:
            self.validate(data)
            return True
        except (ValidationError, ValueError):
            return False

Baseline Classifiers #

Two non-LLM baselines establish a lower bound for comparison. Both implement a classify(package) -> str interface and return a failure category with no API calls.

KeywordClassifier (evaluation/baselines/keyword.py · 75 lines) #

A weighted 3-tier scoring system with disambiguation. Concatenates current_logs, previous_logs, k8s_events_filtered, and pod_status_summary into a single lowercased string, then scans for keywords. Tier 1 (definitive signals) gets weight 3, Tier 2 (strong signals) gets weight 2, Tier 3 (weak/symptom) gets weight 1. The category with the highest weighted score wins; returns "unknown" if no keyword matches. A disambiguation rule halves symptom-category (probe) scores when any root-cause category has a score ≥ 2. Covers 7 categories (no unknown rule):

RuleBasedClassifier (evaluation/baselines/rulebased.py · 132 lines) #

More sophisticated: applies structured rules in priority order, combining text signals with restart_count and event text. First matching rule wins. The priority order is image → resource → config → dependency → probe → crash → network. An explain() method returns all matched signals for debugging.

    """Classify an incident using structured rules. First matching rule wins."""
    text = _all_text(package)
    for category in _PRIORITY:

TDD Approach #

The project was developed test-first. Each pipeline stage, provider, and endpoint has a dedicated test file written alongside (or before) the implementation. The pattern is consistent:

  1. Write a failing test that describes the desired behaviour (e.g. "redactor masks sk-... as [OPENAI_KEY=REDACTED]").
  2. Implement the minimum to pass it (add the regex + replacement to REDACT_PATTERNS).
  3. Add edge-case tests (no match, partial match, ordering) and refine.
  4. Run make test-cov and confirm the new code is covered and nothing regressed.

Monitoring Considerations #

  • Health endpoint. GET /health returns {"status":"ok","provider":"..."} — suitable for Kubernetes liveness/readiness probes (both wired to /health in k8s/analyser/deployment.yaml).
  • Structured logs. structlog emits key/value events (analysis_started, analysis_complete, analysis_failed, report_persist_failed) with a request ID — parseable by any log aggregator (Loki, Elasticsearch, Datadog).
  • Persistence visibility. Every report is written to REPORTS_DIR as a timestamped JSON file. A sidecar or cron job could ship these to object storage for long-term audit.
  • LLM cost & latency. The evaluation harness records latency_s per scenario. In production, wrapping provider.analyse() with a metrics emitter (Prometheus histogram) would surface P50/P95 latency and token spend.
  • Failure isolation. The analyse_pod handler catches all exceptions and returns HTTP 500 with the error detail. Persistence failures are downgraded to warnings so a full disk never blocks an analysis response.
  • Resource limits. The analyser container is capped at 500m CPU / 512Mi memory — enough for a single concurrent analysis. Horizontal scaling would require a shared REPORTS_DIR (e.g. a PVC or S3-backed persistence layer).

Research prototype note

This system is a PhD dissertation prototype demonstrating that LLM-assisted log analysis is feasible, schema-safe, and benchmarkable. The architecture is deliberately small (1,406 source lines) so that every component is auditable. Hardening for production would focus on: narrowing CORS, adding authentication, replacing file-based persistence with a database, adding Prometheus metrics, and load-testing the LLM provider path under concurrent requests.
